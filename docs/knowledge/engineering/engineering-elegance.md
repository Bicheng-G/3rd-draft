# 工程优雅：最小充分模型

非平凡设计/重构，或新增 flag/state/fallback/特殊分支/抽象/重复规则/ownership 前读取。

用表达真实问题所需的最少概念、机制和规则，保留必要领域复杂性。先建立根因模型，再改症状；多个例外共享原因时检查缺失的不变量、状态转换、canonical owner 或职责边界。

1. 同一事实尽量只有一个权威表示；真正不同的业务语义不能压成一个 status。本项目收藏、使用、采用与发布就是不同含义。
2. 共享不变量优先于页面/endpoint 例外树；让下一次修改需要同时理解和同步的地方更少。
3. 稳定机制与业务政策分开，不把政策散落在存储、重试、UI、worker；不为此自动新建框架。
4. 模型直接表达实体、关系、生命周期。派生状态注明生产者/消费者及重建方式，不能悄悄成为第二事实源。
5. 重复请求、并发、重试、响应丢失、断网和重入应有自然可测行为。未知状态不掩盖数据错误。
6. 复用语义而非相似代码形状，只抽象已经证明的变化；不为想象中的扩展建 provider/factory/framework。
7. 每种含义有明确 owner、表示和转换契约，减少未来重复决策；根因驱动的扩大重构仍受任务范围约束，越界前说明证据、收益、影响和恢复要求。

新增机制前用简短设计说明回答：真实问题是什么，已有概念是否覆盖，能否以一个 invariant/owner/state model 消除多个例外；新增/消除哪些概念；未来改一条规则需改几处；是否改善局部推理、对应真实变化、减少未来决策。简单答案写在任务结果即可，无需另建模板文档。
